## 1. The confirmation token already exists. Extract it; do not write a second one.

`artifacts/api-server/src/routes/invoice-reminder-batch-routes.ts` already implements exactly the interlock #2002 describes, and implements it well:

- `issueConfirmationToken` (:104) and `verifyConfirmationToken` (:124), both already exported
- token format `exp.nonce.hmac`, signed with a key derived from `SESSION_SECRET` (:61)
- `REMINDER_CONFIRMATION_TTL_MS` = 15 minutes (:52), sized so a human can read a list and think
- `spentConfirmations` (:96), a spent-nonce map, so a token authorises exactly one run
- ordering enforced by the server rather than the dialog — the file's header comment says so explicitly

**What blocks direct reuse:** `ConfirmationClaims` (:73) is reminder-shaped — `invoiceIds` and `templateKey` — and `claimsFingerprint` (:80) hardcodes that shape.

**Do this instead of copying the pattern into `budget-routes.ts`:** extract the generic half into a shared module — the token format, `sign`, the TTL, the spent-nonce map, `issueConfirmationToken` and `verifyConfirmationToken` — taking a **caller-supplied fingerprint string** rather than a typed claims object. The reminder route keeps its own `ConfirmationClaims` and `claimsFingerprint` and passes the resulting string in. The bulk-paste route passes its own: actor, company, year, and the canonical sorted row set.

Afterwards there is **one** confirmation implementation with two callers, and the reminder route's behaviour is unchanged. Two copies of an HMAC interlock is the kind of duplication that only shows up as a bug the day one of them is fixed and the other is not.

**Known limitation, now shared:** `spentConfirmations` is an in-memory `Map`, so replay protection is per-process and does not survive a restart. That is acceptable here and should not be over-engineered — the bulk write is already idempotent, since unchanged rows are skipped, so a replayed confirmation writes nothing. Note it in the shared module's comment so the next caller knows what it is getting.

**Add to step 5:** extract rather than reimplement, and add a grep proof that exactly one confirmation-token implementation exists.
