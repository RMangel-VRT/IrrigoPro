**What & Why**
Four tickets in a row added capability to the invoice page — AR columns, flags, filters, reminders, batch send, AR notes — and none of them changed the layout those things landed in. The result is seven filter dropdowns in a row, a Flags column cramming several badges into one cell, and every action buried in a kebab menu.

The bookkeeper feels it worst because her `/` route renders this page directly, so it is her home screen. But it is everyone's invoice page, and it is doing a poor job for all of them.

This ticket redesigns the header, the filters, and the row.

**This is the invoice page for every role that can read invoices** — not a bookkeeper variant. One layout, with capability gates deciding which controls appear. A second invoice surface is how two screens start disagreeing about what is owed.

## This ticket is deliberately not split further

The pieces below are one coherent layout change. A new aging strip above the old seven-dropdown filter row is worse than either endpoint; so is a redesigned row under the old header. **The intermediate states are the problem, not the size.** Ship it as one change or not at all.

## Decisions (fixed — do not relitigate)

- **The aging strip shows for every role with invoice access.** One page, one layout.
- **Default view is role-keyed.** The bookkeeper lands on unpaid-and-overdue, biggest balance first, flat. **Every other role keeps today's month-grouped, newest-first default.** Nobody mid-workflow gets their screen reordered.
- **Common actions inline, the rest in the menu.** View PDF and resync to QuickBooks become inline icons; void, merge, correct and the other structural actions stay in the kebab with their existing confirmations.

## Slice 1 — Header and QuickBooks status

A single header row above everything:

- Title, plus a one-line summary of total outstanding and invoice count **for the current filter**, so it changes as she filters and always describes what is on screen.
- **Replace the current "Total Billed" tile.** The header today reads *"Monthly Invoices — All invoices sent across all customers"* with a **Total Billed $29,096.03** figure. On a collections screen that is the wrong headline number: a bookkeeper is chasing what is **outstanding**, not what was billed. Lead with outstanding balance for the current filter; billed total is not what this page is for.
- A **QuickBooks status pill**: connected state and last sync time, with a sync button beside it. When `paymentSyncedAt` is older than 24 hours or null, the pill takes the warning treatment and says balances may be stale. Gate the pill and button on `CAN_MANAGE_QUICKBOOKS` — a role without it sees **neither**, not a disabled control.
- The pill answers "can I trust this number", so it must be visible without scrolling.

## Slice 2 — Aging strip as the primary filter

Four cards: **Not yet due · 0–29 · 30–59 · 60+**, each with dollar total and invoice count, using the labels and boundaries from `lib/shared/src/invoice-aging.ts`. Do not recompute either.

- **Clicking a card filters the list to that bucket**, with the selected card visibly active. This replaces the aging dropdown entirely — **reuse the existing `?aging=` URL parameter** so Financial Pulse deep links keep working unchanged.
- Totals respect the other active filters, so the strip and the table always agree.
- The aggregate is the one new server read. Company-scoped from the caller's company, never summing across companies, `super_admin` passing an explicit company. Subject to the same pricing-visibility rules as the table.

## Slice 3 — Collapse the filter row

- A **search box** for invoice number and customer.
- One **Filters** button opening a popover with payment status, sent state, reminders, customer, date range, amount range, and flags-only.
- **Active filters render as removable chips** beneath the toolbar, with Clear all. The chips answer "why am I seeing these rows" — an applied but invisible filter is worse than no filter.
- Every filter stays in the URL exactly as today. This is a presentation change to controls that already work; **the query parameters and the server-side filtering must not change.**

## Slice 4 — The row

Five columns: **selection · invoice · balance · status · action**.

- **Invoice** — customer name on top, invoice number and due date beneath.
- **Balance** — amount, with days overdue beneath in the danger treatment when overdue. Falls back to invoice total when no payment sync has run, with the stale indicator alongside.
- **Status is two lines, deliberately.** Top line is what the money is doing (`Unpaid · 60+`, `Paid`, `Never sent`, `Voided in QuickBooks`). Bottom line is what we have done about it (`Sent Jun 2 · 2 reminders`, `Never reminded`, `No PDF on file`, `Needs a decision`). These are different questions and the Flags column mashes them together. **Every existing flag maps into this shape — none are dropped.**
- **One primary action per row, naming the action that applies.** Never sent shows **Send**, not Remind. Inside the reminder throttle shows **In 5 days** rather than a dead disabled button. This is #1887's refusal matrix surfaced as the control itself instead of an error after the click. **Read the refusal reason from the server; do not re-derive eligibility in the client**, or the button and the endpoint will drift.
- **Inline icons** for View PDF and Resync to QuickBooks. **Kebab menu** for void, merge, correct, return to draft, finalize, edit metadata, attach ticket, and audit — all preserved with their current confirmations, moved out of the main row.
- **A note indicator** when AR notes exist, gated on `CAN_READ_AR_NOTES` and stripped server-side by `ar-note-visibility.ts` — absent from the response for roles without it, not hidden in the client.

## Slice 4b — Fix the duplicate Sent badge (and the data behind it)

Visible in production today: Woodglenn Squares HOA and Lake Isle Townhomes each render **two** Sent badges — a lowercase grey `sent` and a green `Sent`.

The cause is two things at once:

1. **`getStatusBadge` has a catch-all `default:` that renders the raw status string** (`invoices.tsx:311–312`). An invoice still carrying `status = 'sent'` falls through and prints `sent` in a grey badge.
2. **`getSentBadge` (`:290`) renders a second, green `Sent`** from `sentAt`, which is correct and is what #1847 intended.

**#1847's backfill did not fully run.** Measured in production, 133 invoices total:

| status | count | with `sent_at` |
|---|---|---|
| paid | 78 | **27** |
| **sent** | **33** | 33 |
| generated | 11 | 0 |
| merged | 9 | 0 |
| superseded | 1 | 0 |
| cancelled | 1 | 0 |

#1847's spec states plainly that after its backfill *"`'sent'` must not appear as a written `status` value anywhere"* and *"every existing sent invoice has a populated `sentAt`"*. Neither held. **33 invoices are still at `status = 'sent'`** — every one of them renders a duplicate badge today, not just the two visible in the screenshot.

**Three things to do, in this order:**

1. **Finish the status migration.** All 33 already have `sent_at` populated, so no timestamp recovery is needed — simply move `status` from `'sent'` to `'generated'`. Verify the count is still 33 at run time and report it; if a row somehow lacks `sent_at`, set it from `updated_at` first as #1847 specified.

2. **Investigate the 51 paid invoices with no `sent_at`** (78 paid, 27 with a timestamp). Some may never have been sent, but the likelier explanation is the bug #1847 was written to fix: payment sync overwrote `status` with `'paid'` before anyone recorded the send, destroying the delivery record. #1847 included a second backfill for exactly this — copy `invoice_pdfs.sent_at` where the PDF record shows the invoice was emailed but the invoice itself has no `sentAt`. **Report how many of the 51 have a matching `invoice_pdfs` row with a send timestamp before writing anything.** If the answer is large, that is a delivery history worth recovering; if it is zero, say so and leave them.

3. **Replace the `default:` catch-all** in `getStatusBadge`. A status the badge does not recognise should render as a clearly-marked unknown, not leak a raw lowercase database value into the UI. Printing whatever string happens to be in the column is why 33 broken rows sat visible and unnoticed.

Fold this into the two-line status treatment in Slice 4 — same pass, not a follow-up.

## Slice 5 — Selection and batch entry

The selection bar appears when rows are selected, showing count and dollar total, with **Send reminders** and Clear. It is the entry point to #1888's confirmation list, which is **unchanged** — this ticket does not touch the confirmation flow or its skip reasons.

Select-all respects the active filters, so "select what I am looking at" behaves as expected. Gate the bar on `CAN_SEND_INVOICE_EMAIL`.

## Capability gates — the whole point of one page

| Control | Gate |
|---|---|
| Page, aging strip, filters, table | `CAN_READ_INVOICES` |
| Remind, Send, selection bar, batch | `CAN_SEND_INVOICE_EMAIL` |
| Void, merge, correct, finalize, return to draft, edit metadata, attach ticket, create invoice | `CAN_EDIT_INVOICES` |
| QuickBooks pill, sync, resync | `CAN_MANAGE_QUICKBOOKS` |
| Note indicator | `CAN_READ_AR_NOTES` |

Every gate uses `hasCapability` from `lib/shared/src/roles.ts`. **No role-string comparisons anywhere in this page.** A control whose gate is looser than the endpoint behind it is a button that 403s — audit for that explicitly and report what was found.
